02 · Qué pedía el ejercicio
  • Recibir una necesidad técnica en lenguaje natural.
  • Recibir un lenguaje de programación.
  • Devolver top 5 repositorios de GitHub.
  • Mostrar nombre + URL, descripción y última actividad.
  • Agregar recomendación corta y explicar por qué es “mejor”.
  • Evitar ranking puramente por stars.
  • Contemplar abandonados, forks, tutoriales y candidatos débiles.
  • Incluir 3 ejemplos de uso en README/salida.
03 · Problema con GitHub Search plano

Plain search

  • Keyword match.
  • Sesgo a popularidad.
  • Sin explicación.
  • Sin modelo de calidad.

Sift

  • Entiende query y dominio.
  • Construye variantes neutrales.
  • Extrae señales.
  • Rankea por múltiples factores.
  • Explica tradeoffs y riesgos.
04 · Arquitectura del sistema
User query → normalize → classify domain → generate query variants → GitHub Search API → dedupe candidates → feature extraction → deterministic scoring → explanation → UI / Markdown / report
Nota: la IA puede asistir redacción de explicaciones, pero el ranking se mantiene determinístico.
05 · Query understanding
  • Normalización de consulta natural.
  • Detección de dominio técnico.
  • Eliminación de trampas léxicas.
  • Generación de variantes neutrales.
  • Sin inyección hardcodeada de repos canónicos.
"Edit PDFs in Python" → variantes orientadas a pdf/document processing/library "JWT auth" → variantes de jwt/token authentication "ORM python" → variantes de orm/database mapping
06 · Feature extraction

Grupos de señales

  • Relevance
  • Maintenance
  • Documentation
  • Community
  • Modernity
  • Authority-like signals
  • Risk penalty

Ejemplos por grupo

  • Maintenance: última actividad, issues/forks/license.
  • Documentation: README, instalación, uso, ejemplos.
  • Risk: tutorial/demo/example, app full-stack cuando se pidió librería, archived/fork/toy.
07 · Scoring formula
total = relevance * 0.30 + maintenance * 0.20 + documentation * 0.15 + community * 0.15 + modernity * 0.10 + authority * 0.10 - riskPenalty
  • Relevance (30%): match técnico real con la necesidad.
  • Maintenance (20%): probabilidad de uso mantenible.
  • Documentation + Community (30%): capacidad de adopción.
  • Modernity + Authority (20%): vigencia y señales de confianza.
  • Risk penalty: corrige demos, tutoriales o candidatos engañosos.
El scoring es determinístico y auditable: mismo input, mismo orden y mismos puntajes.
08 · Tres ejemplos requeridos

Ejemplo 1 · “Edit PDFs in Python” (python)

  • Qué espero: librerías de procesamiento PDF/documento por encima de editores de texto o tutoriales.
  • Qué muestro en vivo: top 5, score por señales, y caveats para repos stale/tutorial.
  • Qué revisar: coherencia entre necesidad y tipo de repo recomendado.

Ejemplo 2 · “JWT auth” (python)

  • Qué espero: librerías reutilizables de JWT/auth por encima de apps tutorial full-stack viejas.
  • Qué muestro en vivo: impacto de maintenance y adopción en el ranking final.
  • Qué revisar: explicación de tradeoffs cuando un repo es popular pero riesgoso.

Ejemplo 3 · “ORM python” (python)

  • Qué espero: librerías de mapeo ORM por encima de demos genéricas.
  • Qué muestro en vivo: peso de docs + mantenimiento en el orden.
  • Qué revisar: si el ranking refleja uso real en proyectos productivos.

Importante: durante la grabación no inventar resultados. Mostrar salida real actual de la app.

09 · Explanation layer
  • La explicación determinística es la fuente de verdad.
  • No debe afirmar actividad reciente si un repo está stale.
  • No debe afirmar adopción fuerte en repos de baja señal.
  • Agrega caveats para licencias copyleft y riesgo tutorial/demo.
Gemini (opcional): - Puede reescribir explicaciones para legibilidad. - No rankea. - No cambia score ni orden. - Si falta GEMINI_API_KEY, fallback seguro.
10 · Rate limits y auth
  • GitHub API anónima tiene límites estrictos.
  • GITHUB_TOKEN puede funcionar como fallback del servidor.
  • GitHub OAuth permite usar token propio del usuario.
  • En producción conviene cachear metadata para bajar costo/latencia.
11 · Qué mejoraría para 100+ devs
  • Cache persistente.
  • Background workers.
  • Cola para extracción de features.
  • Señales extra desde PyPI/NPM (descargas/adopción).
  • Observabilidad end-to-end.
  • Saved searches / historial.
  • Analítica de uso por equipo.
  • Estrategia robusta de timeout/retry.
  • Deploy con mayor timeout de funciones server.
12 · Uso de IA
  • El uso de IA fue parte obligatoria del ejercicio.
  • La IA se usó como asistencia de ingeniería.
  • Los prompts ayudaron a iterar frontend, scoring, docs y auditoría.
  • El ranking final sigue siendo determinístico.
  • El LLM no decide silenciosamente la respuesta.
13 · Cierre

Sift no es sólo un GitHub Search más lindo.

Es una capa de ranking explicable sobre metadata de GitHub, diseñada para ayudar a developers a elegir mejores repositorios más rápido.
