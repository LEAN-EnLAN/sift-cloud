01

Qué pedía la consigna

No era “usar GitHub Search”. Era decidir y defender qué significa que un repositorio sea mejor.

Input

  • Necesidad técnica en lenguaje natural
  • Lenguaje de programación
  • Filtros opcionales como stars, fecha o licencia

Output

  • Top 5 repositorios
  • Nombre + URL
  • Descripción y última actividad
  • Recomendación corta y criterio de ranking
speaker cue“La parte central no es traer resultados; es explicar por qué esos resultados son mejores que otros.”
02

Dos implementaciones

Hice una versión terminal-first y una versión Cloud visual. Resuelven el mismo problema desde dos contextos de uso.

Sift CLI

Herramienta para terminal, scripts, CI y agentes. Tiene TUI, salida JSON, modo agente, speed tiers y cache local.

$ sift -q "autenticación con JWT" -l Python --top 5 $ sift --agent --query "procesar PDFs" --language Python $ sift --speed thorough -q "boilerplate de FastAPI" -l Python

Sift Cloud

Companion web para demo y revisión. Muestra score, explicación, metadata, auth con GitHub y breakdown visual.

Query → GitHub API → Feature extraction → Scoring → Explanation → UI
03

Por qué CLI primero

La CLI está más cerca del flujo real de un desarrollador.

Terminal

Permite buscar sin salir del entorno de trabajo.

Automatización

El modo JSON/agent sirve para scripts, CI y otros agentes.

TUI

Si no pasás flags, podés usar una interfaz interactiva en terminal.

speaker cue“Cloud no reemplaza la CLI: la hace más fácil de mostrar y revisar visualmente.”
04

Problema con GitHub Search plano

GitHub puede traer repos populares, pero no necesariamente convenientes.

GitHub Search básico

  • Keyword match
  • Sesgo por popularidad
  • No explica tradeoffs
  • Puede traer tutoriales o repos abandonados

Sift

  • Genera variantes
  • Deduplica candidatos
  • Extrae señales
  • Rankea localmente y explica
05

Arquitectura compartida

CLI y Cloud son interfaces distintas sobre la misma idea de producto.

1. QueryLenguaje natural + lenguaje técnico.
2. UnderstandingNormalización, dominio, variantes.
3. GitHub APISearch API + metadata + README/commits.
4. RankingScoring determinístico + explicación.
User query → normalize → classify domain → build query variants → GitHub Search API → dedupe candidates → extract features → deterministic scoring → CLI / TUI / Agent JSON / Cloud UI
06

Query understanding

La búsqueda no es una sola query grande. Son variantes enfocadas.

procesar PDFs

Dominio: PDF / document processing. Evita caer en editores genéricos.

autenticación con JWT

Dominio: JWT / token auth. Prioriza intención técnica.

ORM python

Dominio: database mapping / ORM. Penaliza demos si la intención es librería.

speaker cue“No hardcodeo un ganador final. El sistema mejora generando mejores candidatos y rankeándolos por señales.”
07

Feature extraction

Cada candidato se enriquece antes de rankearlo.

Mantenimiento

Último commit, archivado, forks, licencia, presión de issues.

Documentación

README, instalación, usage, examples, comandos y badges.

Riesgo

Tutoriales, demos, toy projects, full-stack apps cuando se busca librería.

starsforksREADMElast commitlicenserisk flagscache
08

Scoring

La CLI documenta una fórmula simple y defendible. Cloud evoluciona la misma idea con más señales.

score_base = 35% relevancia + 25% actividad + 20% comunidad + 10% documentación + 10% mantenimiento score_final = score_base * (0.65 + 0.35 * relevancia)

Por qué relevance gate

Evita que un repo enorme gane si no resuelve exactamente la necesidad.

Por qué log community

Evita que 50k stars aplasten automáticamente a un repo más chico, activo y específico.

11

Rate limits y auth

La principal restricción real es la API de GitHub.

CLI

  • OAuth device flow con sift --login
  • GITHUB_TOKEN manual
  • Cache local en .cache/sift
  • Speed tiers para controlar profundidad

Cloud

  • GITHUB_TOKEN como fallback
  • OAuth opcional
  • Feature extraction con rate-limit handling
  • Gemini opcional solo para explicación
12

Uso de IA

La IA se usó como asistencia de ingeniería, no como autoridad silenciosa del ranking.

Usé IA para

  • Iterar prompts y arquitectura
  • Frontend y documentación
  • Auditar errores
  • Refactorizar scoring y explanations

No uso IA para

  • Decidir qué repo gana
  • Cambiar scores
  • Reordenar resultados
  • Inventar facts de repos
speaker cue“La decisión principal fue no confiar el ranking a una caja negra. La IA puede redactar mejor, pero no decide.”
13

Cómo lo escalaría a 100+ devs

La versión actual resuelve el ejercicio; una versión de equipo necesita infraestructura.

Backend compartido

GitHub App token, no depender de tokens personales.

Cache distribuido

Cache por query normalizada y por repo enriquecido.

Workers

Cola async para README, commits, releases y contributors.

Señales externas

PyPI/NPM downloads, dependents, release cadence.

Feedback loop

Útil/no útil para ajustar pesos o entrenar ranker futuro.

Observabilidad

Rate limit, latencia, cache hit ratio, queries sin buenos resultados.
